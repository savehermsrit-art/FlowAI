1.1 Problem statement
Elderly citizens in Karnataka often struggle to discover and apply for pension, healthcare, insurance, and financial-assistance schemes. Relevant information is scattered across government websites, circulars, notifications, and application portals. Eligibility conditions may be complex, difficult to interpret, and unavailable in accessible language.
Many scheme-discovery workflows rely heavily on self-declared answers or generic filtering criteria. They do not consistently provide document-backed preliminary eligibility assessment, condition-level explanations, or personalized guidance about missing evidence.
Consequently, citizens may struggle to determine which schemes are relevant to them, what evidence they need, and how to prepare an application.
These difficulties are amplified by limited digital literacy, language barriers, low-quality document scans, and the need for caregiver assistance.
1.2 Proposed solution
FormFlow AI provides a unified interface where elderly citizens or authorized caregivers can upload relevant documents, review extracted information, and receive evidence-backed preliminary eligibility assessments for curated Karnataka welfare schemes.
The system combines:
Kannada and English OCR.
Document classification and structured information extraction.
User confirmation and correction of extracted fields.
Deterministic rule-based eligibility evaluation.
Three-valued logic.
Human-reviewed, version-controlled government scheme rules.
Retrieval-augmented explanations based on official source documents.
Missing-document identification.
Personalized document checklists.
Ranked scheme recommendations.
Kannada and English interface.
Accessible voice-assisted interaction.
Caregiver-assisted workflows.
Government-source change monitoring.
Administrative review and approval.
Consent, privacy, access controls, and retention management.
The application must distinguish preliminary guidance from an official government eligibility decision.
FormFlow AI cannot approve benefits, certify document authenticity, guarantee scheme acceptance, or replace the responsible government department.

8. DETERMINISTIC ELIGIBILITY RULE ENGINE
This is the central technical component of FormFlow AI.
Only this engine may determine eligibility-condition results and aggregate preliminary eligibility verdicts.
The engine must not depend on:
An LLM.
Network calls.
Database queries.
Randomness.
External state.
Hidden mutable configuration.
Implement it as a pure Python module.
The same facts, evaluation date, and rule version must produce exactly the same result.
8.1 Rule representation
Use a structured JSON or YAML rule DSL.
Each rule condition must identify:
Unique condition ID.
Human-readable description.
Fact key.
Operator.
Comparison value.
Data type and units.
Allowed evidence types.
Applicable document validity rules.
Required official source clause.
Reason codes.
Applicable effective period where relevant.
Support comparison operators:
Equal.
Not equal.
Greater than.
Greater than or equal.
Less than.
Less than or equal.
Membership.
Range.
Existence.
Support nested logical expressions using:
AND.
OR.
NOT.
Do not use arbitrary Python eval() or executable expressions from rule files.
Validate the DSL against a strict schema.
8.2 Three-valued logic
Every condition must evaluate to exactly one of:
SATISFIED
NOT_SATISFIED
INSUFFICIENT_EVIDENCE
Internally implement TRUE, FALSE, and UNKNOWN using Kleene three-valued logic.
AND:
FALSE if any input is FALSE.
UNKNOWN if none is FALSE and at least one is UNKNOWN.
TRUE if all inputs are TRUE.
OR:
TRUE if any input is TRUE.
UNKNOWN if none is TRUE and at least one is UNKNOWN.
FALSE if all inputs are FALSE.
NOT:
TRUE becomes FALSE.
FALSE becomes TRUE.
UNKNOWN remains UNKNOWN.
Implement exhaustive truth-table tests.
8.3 Missing and conflicting evidence
Return INSUFFICIENT_EVIDENCE when an appropriate condition cannot be established.
Support reason codes such as:
MISSING_DOCUMENT
MISSING_FIELD
LOW_OCR_CONFIDENCE
UNCONFIRMED_FIELD
CONFLICTING_EVIDENCE
EXPIRED_DOCUMENT
UNSUPPORTED_DOCUMENT
UNVERIFIED_CORRECTION
AMBIGUOUS_VALUE
These are examples, not substitutes for a properly documented reason-code taxonomy.
Missing evidence must never automatically be interpreted as a failed eligibility condition.
Likewise, an explicitly verified failing condition must not be hidden merely because another condition lacks evidence.
8.4 Rule validation
Reject publication when:
Required rule values are null.
A condition has no valid source clause.
A referenced fact key is unknown.
A logical expression references an undefined condition.
Numeric units are inconsistent.
Dates are invalid.
Mandatory evidence metadata is missing.
Rule semantics cannot be evaluated.
Required regression tests are absent or failing.
A new rule must be reviewed and explicitly approved before becoming active.
8.5 Aggregate verdicts
Produce one of three preliminary scheme-level verdicts:
LIKELY_ELIGIBLE
NEEDS_EVIDENCE
NOT_ELIGIBLE
Mapping:
Root TRUE → LIKELY_ELIGIBLE
Root UNKNOWN → NEEDS_EVIDENCE
Root FALSE → NOT_ELIGIBLE
Always display that a positive assessment does not guarantee government approval.
8.6 Ranking
Rank results deterministically.
Primary order:

Needs additional evidence.
Not eligible.
Within NEEDS_EVIDENCE, prioritize schemes with fewer distinct missing documents, using a stable scheme ID tie-breaker.
Do not present fabricated approval percentages, probabilities, or confidence scores.
